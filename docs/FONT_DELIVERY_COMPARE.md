# 랜딩 Wanted Sans 전송 방식 비교 (2026-11-09)

#6(2026-09-08)에서 로컬 가변 폰트(1.29MB)를 wanted-sans 공식 CDN 서브셋으로 바꿨다. 이 문서는 그 뒤 **2026-11-09에 따로 한 비교 실험**이다. #6 당시 다른 방식과 비교하고 CDN을 고른 기록은 없다. 이 결과를 "그때 비교해서 골랐다"로 쓰지 않는다.

코드는 바꾸지 않았다. 후보는 측정용 브랜치 `measure/font-*`의 Vercel 미리보기 배포로만 띄웠고, 측정이 끝난 뒤 정리했다.

## 해석

### 저속 시뮬레이션 LCP는 폰트 도착 순서에 따라 두 갈래로 갈린다

simulate는 실제로 한 번 로드한 기록(관측 trace)을 바탕으로 저속 네트워크에서의 시간을 추정한다. 관측 로드에서 **ExtraBold가 h1이 그려지기 전에 도착했으면** 추정 LCP에 폰트 다운로드가 들어가고, h1이 대체 글꼴로 먼저 그려졌으면 들어가지 않는 것으로 보인다(Lighthouse 내부 계산을 직접 확인하지는 않았고, 회차별 관측 시각으로 추정했다).

- 이번 P0는 5회 모두 폰트가 먼저 도착해 10.8~11.0s였다. 같은 날 다른 측정과 겹쳐 무효로 돌린 첫 묶음(아래)에서는 P0가 4.5~4.9s인 회차가 3번 있었다. 그중 2번은 관측 로드에서 폰트가 h1보다 늦게 도착했고, 1번은 22ms 먼저 도착했다. 나머지 2번(11.0s)은 폰트가 약 100~120ms 먼저 도착했다.
- 그래서 가변 폰트처럼 큰 폰트는 simulate 값이 회차에 따라 크게 흔들릴 수 있다. 11-05 재측정의 "전 10.74s"는 이번 P0(10.98s)와 같은 갈래로 보인다(11-05 원본 JSON으로 확인하지는 않았다).

### 히어로 제목은 JS 실행 뒤에 그려진다

랜딩은 클라이언트 렌더링이라 h1이 번들 JS 실행 뒤에 DOM에 들어간다. 관측 로드에서 번들 JS는 약 0.16~0.39s에 끝났고 h1은 약 0.6~0.99s에 그려졌다. preload한 ExtraBold는 약 0.19~0.30s에 이미 도착했는데도(D, E, G) h1은 다른 후보와 비슷한 시점에 그려졌다. 그래서 이 페이지에서 preload는 LCP를 당기지 못했다.

### 그래서 바이트 총량이 갈랐다

자체 호스팅 후보끼리 렌더 차단 요청 수(3)는 같다. 그런데 LCP는 전송량 순서대로 나왔다(F 314KB 5.28s < C 852KB 6.62s ≈ B 1.03MB 6.65s). 폰트 요청은 우선순위가 높아(VeryHigh) 저속 회선에서 JS와 대역폭을 나눈다. 받는 글자 범위를 페이지가 실제로 쓰는 글자로 좁힌 것이 이번 비교에서 효과가 컸던 것으로 보인다. 요청별 기여를 나눠 재지는 않았다.

공식 CDN(A)은 92조각 중 실제로 나온 글자의 조각만 받아 KS X 1001 전체(B, C)보다 바이트가 적다. 대신 CSS 5개가 렌더를 막고 요청이 37개다. 둘이 상쇄되어 B, C와 LCP가 비슷하게 나온 것으로 보인다.

## F 방식의 트레이드오프

- **글자 범위**: 소스 코드에 있는 505자만 담는다. API나 사용자 입력에서 오는 글자(부스 이름, 롤링페이퍼 글 등)가 목록에 없으면 그 글자만 Pretendard로 그려져 글꼴이 섞여 보인다. 축제 기간처럼 서버 데이터가 화면에 나오는 경우에는 C(KS X 1001 + `unicode-range`)를 뒤에 대비용으로 함께 두는 구성을 따로 재 봐야 한다.
- **유지 비용**: 문구를 바꿀 때마다 글자 목록을 다시 뽑아 잘라야 한다. 빌드 단계에서 자동으로 하지 않으면 빠지는 글자가 생긴다.
- **라이선스**: Wanted Sans는 SIL OFL 1.1이고 "Wanted Sans"가 예약 글꼴 이름이다. 서브셋 파일을 직접 배포할 때 이름을 그대로 써도 되는지는 확인하지 않았다(이번에는 측정용 미리보기에만 배포했다).
- **외부 의존**: 공식 CDN(jsdelivr)에 의존하지 않게 된다. 대신 폰트 파일을 저장소에 두고 캐시 정책을 직접 관리해야 한다.

## 무효로 돌린 측정

- **같은 날 첫 simulate 묶음(22:22~22:31)**: 같은 맥에서 다른 측정(헤드리스 Chrome 2개로 영상 재생)이 22:20~22:30에 함께 돌았다. simulate는 관측된 CPU 작업 시간을 늘려 쓰므로 영향을 받을 수 있어 통째로 다시 쟀다. 위 simulate 표는 다시 잰 값이다. 첫 묶음의 중앙값도 P0를 빼면 다시 잰 값과 0.1s 안에서 같은 순서였다(F 5.28s, G 5.60s, A 6.63s, B 6.64s, C 6.64s, D 6.78s, E 6.76s, PROD 6.41s).
- **로컬 `vite preview` 비교(21:23~21:48)**: 후보를 로컬 서버에서 쟀으나 같은 시간대에 다른 측정이 함께 돌았고, 로컬 서버는 배포와 응답 조건이 달라 이 문서의 결론에 쓰지 않았다.

## 하지 않은 것

- `/` 외 페이지(`/instating`, `/stamptour` 등)는 재지 않았다. 다른 페이지는 LCP 요소와 쓰는 굵기가 다를 수 있다.
- 실사용자 값(RUM)은 없다. 축제 서버가 내려가 있어 실제 트래픽 조건을 만들 수 없다.
- F와 C를 함께 두는 구성(자주 쓰는 글자 + KS X 1001 대비용), `font-display: optional`, 굵기 수 줄이기는 재지 않았다.
- `develop`에는 아무것도 반영하지 않았다. 방식을 바꿀지는 따로 정한다.
